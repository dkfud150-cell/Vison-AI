# 문서 자동화 — 트리거형 안전관제

관제와 문서 자동화는 **한 프로그램**이다. 왼쪽 사이드바에 메뉴 묶음이 둘 있고 — **관제**(지금 일어나는 일)와
**문서 자동화**(그 일이 남기는 법정 의무와 문서) — 이 폴더는 그중 문서 자동화 묶음 다섯 화면이다.
관제 화면에서 감지 내역을 **문서 자동화로 넘기면**(관제 인계) 여기서 보고서 초안을 만들고, 사람이 확정하면
그 결과가 다시 관제 규칙셋으로 돌아간다. 관제 화면 코드는 새로 만들어 같은 틀에 붙인다.

**원칙** — 숫자는 코드가 계산하고, 문장만 AI가 쓰고, 확정은 사람이 한다.

파일마다 무엇이고 언제 여는지, 시연용 샘플과 사람이 고쳐야 할 곳은 [`파일안내.md`](파일안내.md)에 따로 정리했다.

## 실행

```bash
pip install -r requirements.txt
python run_demo.py              # 화면 없이 문서 전부 생성 → outputs/
python app.py                   # 문서 자동화만 → http://127.0.0.1:7860
```

샘플(기능 확인용 예시) 데이터는 폴더 맨 위 `예시데이터_삭제가능/문서자동화/` 에 있다 — 이벤트 51건 · 프레임 · 허가서 · 제보 ·
시연 날짜(2026-10-12) · 샘플 사고 · 가상 담당자. 폴더를 지우면 `records/` 와 `config/` 만으로 돈다.

관제까지 한 프로그램으로 띄우려면 폴더 맨 위에서 `python app.py` (관제 여섯 + 문서 자동화 다섯 메뉴).
여기 `docgen/app.py` 는 문서 자동화 다섯 메뉴만 띄운다. 이때 관제 엔진(monitor_engine) 결과를 넘겨 보려면 **안전 문서 › 관제 인계 › 관제 엔진 결과 파일로 넘기기**에
`events.jsonl` 이나 `events_for_docgen.json` 을 올리고, 프레임이 있으면 그 파일이 있던 폴더를 적는다.

처음에는 `LLM_PROVIDER=mock` 으로 API 키 없이 돈다 (mock/ 폴더의 미리 써 둔 답).
실제 LLM을 쓰려면 `.env.example` 을 `.env` 로 복사하고 키를 넣은 뒤 `LLM_PROVIDER=claude` 또는 `openai`.
화면에서는 사이드바 아래 드롭다운(문장 생성 · mock / Claude / OpenAI)으로 바꾼다.
Python 3.10 이상. Gradio 6에서 동작을 확인했다. 사이드바(gr.Sidebar) 때문에 Gradio 5는 5.16 이상이어야 한다.

**시연 시계** — `config/site_profile.json` 의 `demo_today`(2026-10-12)가 있으면 서명 · 발행 · 접수 날짜가 그날로 찍힌다.
샘플 데이터와 날짜가 어긋나지 않게 하려는 것이다. 실제 운영에서는 이 줄을 지운다.

**발표장에서는 캐시로** — 실제 API로 한 번 돌리면 결과가 `cache/` 에 저장되고 같은 입력이면 다시 부르지 않는다.
시연 전날 `python run_demo.py --provider claude` 로 한 번 돌려 두면 네트워크와 상관없이 같은 결과가 나온다.

## 화면 — 사이드바 ‘문서 자동화’ 묶음 다섯 개

| 화면 | 하는 일 | 코드 |
|---|---|---|
| 홈 | 오늘 처리할 것(확정 대기 · 기한 임박 · 미조치), 구역 · 모드별 문서 상태판, 관제 기록 증빙 누적, 마지막 관제 인계 | `home.py` |
| 의무 이행 관리 | ‘해야 할 일’ — 사업장 조건별 법정 의무 · 근거 조문 · 기한 · 서류 보존, 구분 필터, 이행 처리 / ‘이행 완료’ — 이행한 기록만 모아 보기 | `compliance.py` |
| 안전 문서 | **관제 인계** · 위험성평가표 · 시정지시서(이미지 분석 포함) · 작업허가서 점검 · 산업재해조사표 | `handoff.py` `assessment.py` `corrective.py` `ptw.py` `accident.py` |
| 안전소통 | 근로자 제보 접수 · 조치, 위험성평가 근로자 확인(확정) | `voice.py` |
| 기록 | 모든 문서 · 보존 기한, 개선 효과 실측, 위험성평가 개정 로그, 규칙셋 개정 이력 | `archive.py` |

화면 코드는 `safety_docs/ui.py`(다섯 화면), 사이드바 틀은 `safety_docs/shell.py` 다. `app.py` 는 틀에 이 묶음 하나를 넣어 띄우는 몇 줄뿐이다.

## 관제 인계 — 감지 내역을 넘겨 보고서 만들기

관제 화면의 **문서 자동화로 넘기기** → `safety_docs/handoff.py` 의 `receive()` → **안전 문서 › 관제 인계** 화면이 열린다.

1. **받기** — 감지(엔진 `kind` = stage · check)만 이벤트로 합친다. 위반 순간 프레임은 `records/monitor_frames/` 로 복사하고,
   내역은 `records/monitor_events.jsonl`, 인계 한 건은 `records/handoffs.jsonl` 에 한 줄씩 **추가**된다.
   같은 내역을 두 번 넘기면 두 번째는 건너뛰고, 번호만 같은 다른 내역(엔진을 여러 번 돌린 경우)은 `-2` 를 붙여 받는다.
   게이트 · 사고 기록은 이벤트에 섞지 않고 인계 기록에만 남긴다 — 위험도 집계를 흐리지 않게.
2. **만들 수 있는 보고서** — 코드가 고른다. 시정지시서(경보 이상), 수시 위험성평가 제안(위험도 12 · 중대성 4),
   작업허가서 점검(게이트가 막은 기록), 산업재해조사표(사고 기록 — 재해자 정보는 사람이 넣는다).
3. **만들기** — 넘기는 것만으로는 아무 문서도 발행되지 않는다. 고른 이벤트로 시정지시서 초안(워드)을 만들면
   발행 기록이 남고 의무 이행 관리에 조치 기한이 올라간다. 위험성평가는 ‘위험성평가로’ 버튼으로 가서 평소 순서대로 한다.

넘어온 내역은 샘플 이벤트와 합쳐져 홈 · 위험성평가 · 의무 이행 관리 · 기록의 집계에 바로 들어간다(`config.load_events()`).
엔진 결과를 넘겨 시험할 때 샘플의 같은 시각(10-12 09:15 등)과 겹쳐 세어지는 게 싫으면 `.env` 에 `DOCGEN_SAMPLE_DATA=off`.

## 한 프로그램 — 관제와 합친 진입점

관제 대시보드와 문서 자동화는 한 프로그램이다. 폴더 맨 위(`안전관제/`)의 `app.py` 가 진입점이고,
관제 여섯 화면(`control/pages.py`)과 이 묶음(`safety_docs/ui.py`)을 같은 틀(`safety_docs/shell.py`)에 넣는다.

```
python app.py            ← 안전관제/ 폴더에서. 관제 + 문서 자동화 (사이드바 11개 메뉴)
python docgen/app.py     ← 문서 자동화만 (관제 인계는 엔진 결과 파일로 받는다)
```

틀이 묶음 사이에 주는 연결 (`ctx.refs`, 모든 화면을 만든 뒤 `ctx.after` 안에서 쓴다):

| 이름 | 하는 일 | 관제에서 쓰는 곳 |
| --- | --- | --- |
| `docgen.open_handoff(event, hid_state)` | 넘긴 뒤 안전 문서 › 관제 인계를 열고 그 인계를 고른다 | 실시간 관제 · 이벤트 로그 · 재생 비교의 '문서 자동화로 넘기기' |
| `docgen.open_tab(event, tab, value_state)` | 안전 문서의 탭을 연다 — `co`(이벤트 번호) · `ptw`(허가서 번호) · `ra` · `acc` | '시정지시서 초안으로' · '작업허가서 점검으로' · '위험성평가에서 확정' |

- `ctx.page(id)` 안에 화면을 만든다. 메뉴에 적은 id 는 전부 만들어야 한다.
- `ctx.on_show(id, fn, inputs, outputs)` — 그 화면을 열 때마다 부른다(최신 기록으로 다시 그리기).
- `ctx.link(button, id)` — 화면 안 버튼으로 다른 화면 열기. `ctx.goto_event(event, id)` 는 앞 이벤트가 성공했을 때만 화면을 옮긴다.
- 관제는 기록할 때마다 `handoff.receive(..., auto=True)` 로 자동 인계한다(집계 · 증빙 누적용 — 관제 인계 목록에는 숨김).
  버튼으로 넘긴 것만 관제 인계 목록에 보인다. 이미 받은 내역을 다시 넘기면 중복으로 건너뛰고 보고서 후보에는 그대로 들어간다.
- 작업허가서 · 격리 목록의 입력 창구는 관제의 격리 목록 대조 화면 한 곳이다. 저장은 `handoff.register_ptw(ptw, isolation)` →
  `records/ptw/` 이고, 문서 자동화의 작업허가서 점검은 읽기만 한다.
- 오탐 표시는 관제 이벤트 로그에서 누르고 `records/false_positive_marks.jsonl` 에 쌓인다(`handoff.mark_false_positive`).
- 구역 이름 · 배관 계통도는 환경 변수 `SITE_PACKAGE`(맨 위 app.py 가 넣는다)가 가리키는 사업장 패키지 `site.json` 이 원본이다.
  문서 자동화만 띄우면 `config/rulesets.json` · `config/piping.json` 을 쓴다.
- 위반 이름은 엔진 규칙(rules.json)의 `violation` 과 `config/scales.json` 의 `severity_by_violation` 이 글자까지 같아야 중대성이 맞게 붙는다.

## 이행 처리

- **담당자** — 직접 치지 않고 `config/staff.json` 목록(이름 · 부서 · 직책)에서 고른다. 기록에는 id · 이름 · 부서 · 직책이 같이 남는다.
  사람을 더하거나 바꾸려면 이 파일을 고친다(의무 이행 관리 탭을 다시 열면 새로 읽는다). 한 번 쓴 id 는 바꾸지 않는다. 지금 이름은 샘플이다.
- **이행일** — `2026.10.10` · `2026/10/10` · `20261010` · `2026년 10월 10일` · `10/10`(연도는 기준일 연도) 모두 받아서
  칸을 벗어나거나 Enter 를 치면 `2026-10-10` 으로 바뀐다. 저장도 이 양식으로만 한다. 읽을 수 없는 값이나 기준일보다 뒤인 날은 받지 않는다.
- **이행 완료** — 직접 처리한 기록(`records/compliance_done.jsonl`), 위험성평가 확정으로 자동 인정된 정기 · 수시평가,
  도입 전 마지막 실시일(`site_profile.json`)을 이행일 순으로 모아 보여 준다. 서류 보존은 이행일부터 계산한 보존 기한까지 적는다.
  부서 · 직책이 없던 옛 기록은 staff.json 에서 같은 이름을 찾아 채우고, 없으면 ‘-’.

## 계산 규칙 (config/scales.json)

- **가능성**: 최근 90일 기본 규칙 위반 건수 → 0건 1 · 1~2건 2 · 3~5건 3 · 6~10건 4 · 11건 이상 5
- **하한**: 최고 경보 1건이면 최소 4, 그 조합의 이벤트가 사고와 이어졌으면 5
- **빼는 것**: 무음(섀도) 기록, 오탐 표시. **따로 세는 것**: 강화 기간(adj_id) 건 — 자기강화 폭주 방지
- **중대성**: 위반 유형별 1~4 (4 = 사망 또는 다수 부상 가능 — 폭발 · 중독 · 질식). ‘산세 구역 화기’ 모드는 하한 3
- **수시평가 제안**: 위험도 12 이상, 또는 중대성 4등급 1건 (위험성평가 지침 제15조제2항)
- **개선 후 위험도**: 예측하지 않는다. 대책 적용일(확정일) 전후 같은 기간의 위반 건수로 실측한다. 적용 후 14일이 안 되면 ‘측정 중’

## 위험성평가 확정 — 두 단계 서명

1. **초안** — 코드가 숫자를, LLM이 문장을 채운다. 감소대책이 규칙셋 변경안(R1~R4)과 같으면 `[공학적·R1]`처럼 연결된다
2. **관리자 서명** (안전 문서 화면) — 문장을 고치고 서명. 이 순간의 내용이 `records/assessments/RA-*.json` 으로 저장된다
3. **근로자 대표 확인** (안전소통 화면) — 확인하면 확정, 반려하면 사유 필수 (산업안전보건법 제36조제2항)
4. **반영** — 확정되면 연결된 규칙 변경(R1~R4)으로 규칙셋 버전이 오르고 `records/ruleset_log.jsonl` 에 남는다

상태는 `records/revision_log.jsonl` 의 마지막 줄이다. 기록 파일은 전부 추가 전용이라 고치거나 지우지 않는다.
두 단계 서명 이전에 만든 확정본(RA-20260929-143501 등)은 그대로 ‘확정’으로 읽힌다.

## 실제 시스템에 붙일 때

- 이벤트: 관제가 넘긴 내역은 `records/monitor_events.jsonl` 에 쌓인다. DB로 옮길 때는 `config.load_events()` 한 곳만
  MySQL events 테이블 읽기로 바꾼다(같은 필드, config.py 주석). 지금 두 코드는 모두 파일(JSONL)로 기록한다
- 프레임: 관제 엔진이 클립과 함께 위반 순간 프레임 1장을 저장하고(`frames/`), 인계 때 `records/monitor_frames/` 로 복사된다
- 작업허가서 · 격리 목록: 샘플은 `../예시데이터_삭제가능/문서자동화/ptw/`, 관제 입력창에서 등록한 것은 `records/ptw/` (`handoff.register_ptw()`)
- 규칙셋: 확정 시 `records/ruleset_log.jsonl` 에 버전이 쌓인다. 관제 엔진이 이 버전의 개정안(R1~R4)을 적용해 돈다
- 화면: 관제와 문서 자동화는 한 프로그램이다. 기본 화면은 폴더 맨 위 `app.py`(화면 시안 그대로의 HTML · `web/`, FastAPI)이고,
  여기 `ui.py` · `shell.py` 는 같은 기능의 Gradio 화면이다(`app_gradio.py` · 단독 실행 `docgen/app.py`). 계산 · 기록 함수는 두 화면이 같이 쓴다
- 알림: 지금은 화면 배너. 실제 운영은 스케줄러가 매일 `build_schedule()` 을 돌려 문자 · 메일로 보낸다
